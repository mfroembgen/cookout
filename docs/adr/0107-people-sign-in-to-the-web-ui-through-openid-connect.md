# People sign in to the web UI through OpenID Connect

2026-11-25. A patch of this fork (mfroembgen/cookout), not of upstream. Upstream's [ADR 0003](0003-admin-is-a-flag-on-an-identity.md) records that Matt rejected OAuth for the board: auth is a token per identity. This fork keeps that model and adds one more way to get a web UI session, so a team whose people already sign in to an identity provider (WorkOS AuthKit, here) needn't hand out tokens. The fork's owner made the decisions below; where upstream's rules ask for Matt's approval (the new terms, the seam rule for the fake, the `jose` dependency), this fork records the choice here instead.

## Decision

- **Off unless set.** `COOKOUT_OIDC_ISSUER` turns it on; then `serve` refuses to start without `COOKOUT_PUBLIC_URL`, `COOKOUT_OIDC_CLIENT_ID` and `COOKOUT_OIDC_EMAIL_DOMAIN` (`oidc_settings_missing`), and refuses an issuer that isn't https or is on a private host (`oidc_issuer_invalid`) or a public URL that isn't https (`oidc_public_url_insecure`), plain http being allowed for either only on a loopback host, for tests and local runs, and an email domain that isn't one (`oidc_email_domain_invalid`). `COOKOUT_OIDC_CLIENT_SECRET` is optional and sent as `client_secret_post`. `COOKOUT_OIDC_LABEL` names the provider in the web UI (`single sign-on` unless set, blank meaning the default). The settings live in `app/modules/config/lib/server/oidc.ts`, exported through `config/server.ts`, which is at its 300-line limit.
- **Authorization Code with PKCE (S256).** When `COOKOUT_PUBLIC_URL` is itself on a loopback host, `GET /v1/oidc/start` asked on another host (`127.0.0.1` for `localhost`, say) first sends the browser to the same path and kept `return` on the public URL, with no cookie, so the sign-in cookie is set on the host the provider sends the browser back to; on any other public URL it never redirects on the Host, since a proxy in front may rewrite it. On that host it reads `<issuer>/.well-known/openid-configuration`, whose `issuer` must equal the setting, and sends the browser to its authorization endpoint with `state`, a fresh nonce, the challenge and `redirect_uri = <COOKOUT_PUBLIC_URL origin>/v1/oidc/callback`, asking for `openid email profile`. Its `return` names the web UI page to come back to once signed in, and only a login request's or an agent join request's approval page, `#/approve/<user code>` or `#/approve-join/<user code>` with a well-formed code, is kept (checked at `start` and again at the callback); anything else comes back to `/`. The login view on a signed-out approval page links there with that page, so a person who opened a `cookout login` or join link signed out lands on it again. The authorization, token, userinfo and `jwks_uri` endpoints must be https and, unless the issuer itself is on a loopback host, on a global unicast address by text: not `localhost` or a name under it, and no address literal outside global unicast. For IPv4 that refuses every IANA special-purpose block that isn't globally reachable (0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/4, 240/4); for IPv6 it allows only 2000::/3, less 2001::/23, 2001:db8::/32, 2002::/16 and 3fff::/20, and an IPv4-mapped (`::ffff:a.b.c.d`) or IPv4-compatible (`::a.b.c.d`) address is judged by its IPv4 address (NAT64's 64:ff9b::/96 is outside 2000::/3). Brackets and trailing dots are ignored. For an issuer off loopback, every call to the provider (discovery, token, userinfo and the JWKS, which the cookout fetches with the same client and hands to `jose` through `createLocalJWKSet`) also goes through an `undici` dispatcher whose connection resolves a name through its own lookup and refuses it if any address it resolves to is one of those kinds, so a name that resolves, or later re-resolves, to such an address reaches nothing; the refusal is `oidc_provider_failed`, its step ending "on a private address". A name that doesn't resolve is `oidc_provider_failed` too. An address literal never resolves, so the text check is the whole check for one: `serve` refuses an issuer on a private host off loopback (`oidc_issuer_invalid`), and discovery refuses such an endpoint. Discovery runs on each sign-in, so a provider that is down never stops the board from starting.
- **State in a sealed cookie.** `state`, the PKCE verifier, the nonce, an expiry 10 minutes away and the page to come back to go in one HttpOnly, SameSite=Lax cookie (the callback is a top-level navigation from the provider's site), sealed with HMAC-SHA256 under a random key the server makes at boot. On https it is `__Host-cookout_oidc` (Secure, `Path=/`, no Domain); on a loopback http board it is `cookout_oidc`. The callback refuses no cookie or an expired one (`oidc_state_missing`), and a cookie whose seal doesn't check out or whose `state` isn't the one sent back (`oidc_state_mismatch`), so a callback link from another browser signs no one in and a cookie someone else set can't pick the verifier or the nonce. Every answer the callback gives clears the cookie, a refusal, a request limit (429) and a storage failure (503) included, each keeping its status. The key lives in the process: a callback must reach the process that sent the browser to the provider, so the board runs as one replica (as SQLite storage and presence already require), and a restart makes a new key, dropping every sign-in in flight; the person starts again.
- **The ID token is checked.** The token endpoint must answer an `id_token`, verified with `jose` against the provider's `jwks_uri` (RS256 or ES256; keys kept for 10 minutes, as `jose`'s own cache does, and fetched again once for an unknown key ID): `iss` must be the issuer, `aud` must be exactly the client ID (a string, or a list of exactly one entry, it), an `azp`, if there is one, must be the client ID, `exp`, `iat` and `sub` must be there, `exp` and `iat` within 60 s of the server's clock, `iat` no older than 10 minutes, and `nonce` the one in the cookie. The userinfo endpoint's `sub` must be the ID token's. Any of these failing is `oidc_id_token_invalid`, its `details.reason` saying which.
- **The callback's other checks.** A query the callback can't read, such as one giving `state` or `code` twice, is `oidc_state_mismatch`; an `iss` that isn't the issuer is refused (`oidc_issuer_mismatch`, RFC 9207, checked after the state so the refusal keeps the approval page); a provider `error`, or no code, is `oidc_provider_refused`; a discovery, token or userinfo call that fails, takes over 10 s, redirects or answers JSON that doesn't match its Schema is `oidc_provider_failed`. Only `email_verified === true` gets in (`oidc_email_unverified`), and only an address at exactly `COOKOUT_OIDC_EMAIL_DOMAIN`, compared lowercased; a subdomain is refused (`oidc_email_not_allowed`).
- **A person is the provider's account, not their address.** Storage links (issuer, `sub`) to an identity name, unique both ways for an issuer, in its own table (`oidc_links`). The fork's migrations are a list of their own, for SQLite and for Postgres, applied after upstream's and counted in a `fork_schema_version` table, so upstream's lists stay as upstream has them and an upstream migration added later never shares a version number with a fork one. A linked account signs in as its human. Single sign-on only ever makes new humans: an unlinked account's address, its part before `@` lowercased with `.` and `_` read as `-`, must be a plain identity name (`oidc_name_unusable`), and a free name makes a new human (never an admin, its display name the provider's `name`, else its `given_name` and `family_name` joined, trimmed, read from the verified ID token first and then from userinfo (WorkOS AuthKit's userinfo has only `sub`, `email` and `email_verified`), else none) and its link in one Storage step. A taken name, a human's, an admin's or an agent's, is `oidc_name_taken`, and the login view tells the person to ask an admin. There is no way to link an account to an identity that already exists: a person who was on the board before single sign-on keeps logging in with their token, and their name gets no single sign-on. Renaming an identity changes only its display name and an identity with messages can't be deleted, so neither frees the name. When creating finds the account already linked, the callback reads that link, so a race lost to another sign-in of the same account ends as that account's human. A linked human that is Deactivated can't sign in (`identity_deactivated`). Deleting an identity deletes its links: `oidc_links.identity_name` references `identities` with `ON DELETE CASCADE` (SQLite's foreign keys are on), so upstream's own delete removes them too, and a board rolled back to upstream that deletes a linked human and makes the name again never hands that name to the old account. A later sign-in never touches the display name, so one the person set stays.
- **The link shows who signs in, to them and admins.** A link keeps the lowercased address the provider verified, updated on each sign-in that gets a session, and when it was made. `GET /v1/whoami` and `GET /v1/identities/:name` add `signIn: { email, linkedAt }` for a human linked at the configured issuer when the caller is that human or an admin; anyone else, and every other route that answers `IdentityResponse`, gets no `signIn`. Both answers, and every answer of `start` and the callback, carry `Cache-Control: no-store`. The profile panel shows it as "Signs in with <label> · <email> · linked <date>" and shows nothing for an unlinked human. It reads the profile afresh each time the profile opens and again whenever the viewer changes (a login, a logout, another name or a change of admin flag), keeps nothing between openings or viewers, drops an answer that arrives after its profile closed or the viewer changed, and draws the line with the provider's name as it stands at each render, so a name that loads after the profile still shows. The web UI shows the session first and asks `GET /v1/sign-in` beside it, so a slow or hanging answer never holds up the token form; it keeps the first answer that succeeds (a later one, such as a timed-out request answering late, changes nothing), asks at most once at a time, and asks again at the next session change after a failure or once a request has gone 5 s unanswered.
- **Single sign-on never grants admin.** It makes only non-admin humans and never reaches an existing identity, so it can't sign anyone in as an admin. Admins promote a human it made, as they would any other.
- **The web session.** The callback issues a Login credential (ADR 0103) with host `web UI (single sign-on)` and sends the browser on (below). Issuing it is the Storage step that reads the link: it issues only while the link the callback found, by a random ID each link gets when it is made, is still there for the same (issuer, `sub`) and human and the human is active, so a link deleted and made again by another sign-in in between, even within the same millisecond, isn't taken for it (a returning human's link is the one read first, a new human's is the one the callback just made, and the link is read again only when making it finds the account already linked by a sign-in that won the race), so a deactivation, a deletion with the name made again, or a removed link between reading the link and issuing leaves no session; the same step says why (`identity_deactivated` when the human is now Deactivated, else `oidc_sign_in_changed`, also when the link vanishes between creating and reading it back) and, only when it issues, stores the address the provider just verified. A human just created is re-checked the same way. The callback then sends the browser to the page the sign-in started from, else `/`. `POST /v1/session` is upstream's. The `cookout_session` cookie is Secure whenever `COOKOUT_PUBLIC_URL` is https, set by `POST /v1/session` and expired by `DELETE /v1/session` alike.
- **Refusals land on the login view.** A refused sign-in answers 302 to `/#/login/<code>` with the refusal as its JSON body, `/#/login/<code>/approve/<user code>` (or `approve-join`) when it started from that approval page and got as far as knowing it, so **Sign in with <label>** there starts again with the same return; the web UI shows `Couldn't sign in (<code>): <message>` from its own text for each code, so a crafted link can't put words on the page. The login view asks `GET /v1/sign-in` (no token) for `{ oidc: false }` or `{ oidc: true, label, start }`, `start` being the absolute `GET /v1/oidc/start` URL on `COOKOUT_PUBLIC_URL`, and, when on, shows **Sign in with <label>** linking to `start` (with any approval `return`) as its main action above the token form, so a board opened on another address it answers to still starts the sign-in on the public host, which stays as the second way in, for the admin's bootstrap token.
- **Open routes.** `/v1/sign-in`, `/v1/oidc/start` and `/v1/oidc/callback` need no token and sit behind the per-address request limit, like the login request routes (ADR 0047). With OIDC off, the two `oidc` routes are no route's (404). The host and origin guard and the CSP are unchanged.
- **CLI logins and agent joins come with it.** The approval pages `#/approve/<code>` and `#/approve-join/<code>` only need a logged-in human in the web UI, so a person signed in through the provider approves `cookout login` and agent join requests as before.
- **Tested against a fake provider.** `app/modules/oidc-fake` is a real local HTTP server, as `webhook-fake` is: discovery, an authorize endpoint that sends the browser straight back with a code for the user it was told to, a token endpoint that checks the client, the `redirect_uri`, the PKCE verifier and that a code is used once and answers an RS256 ID token it signs (its key at `/jwks`; the refusal tests change the next one), and userinfo (with any `name`, `given_name` and `family_name`, and a `sub` a test can fix so an address can change). `.dependency-cruiser.cjs` lists it as a tested interface, keeps it out of the published entries and lets only tests and `testing` reach it.

## Consequences

`jose` 6.2.17 is a runtime dependency, pinned exactly, for the JWT checks against a key set the cookout fetches itself (`createLocalJWKSet`), so the JWKS fetch takes the same guarded path as the other provider calls. The guard uses `undici`, already a dependency, and needs `node:net` and `node:dns` in one adapter, `identities/lib/server/adapters/provider-network.ts`, which `.oxlintrc.json` lets import them; `docs/lint-opt-outs.md` lists it, as a fork decision Matt hasn't confirmed.

Once linked, a person's address no longer names who they are: an address changed at the provider keeps signing in as the same human. A provider that reused `sub` values across people would break this; OpenID Connect forbids it.

Leaving linking out keeps existing identities out of single sign-on's reach, at the cost that a person on the board before it keeps their token login. Turning single sign-on off again doesn't give the humans it made a token they can use: the cookout keeps only a token's hash, so an admin rotates each one's token (`cookout identity rotate <name>`, or **Rotate token** in the web UI) and hands it over.

Proposed terms, decided by the fork's owner rather than Matt: "single sign-on" in the UI, sign-in cookie, link, the provider's label, and the `oidc_*` refusal codes.
