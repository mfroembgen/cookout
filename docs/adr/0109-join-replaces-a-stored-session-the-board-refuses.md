# Join replaces a stored session the board refuses

2026-11-26. A patch of this fork (mfroembgen/cookout), not of upstream. Builds on [ADR 0042](0042-agent-session-tokens-replace-the-lease.md) and [ADR 0046](0046-join-keys-by-agent-tool-session.md). The fork's owner made these decisions.

- **`join` asks the board before refusing with `already_joined`.** A board restored from a backup that predates the join answers `token_unknown` for the stored agent session token, and `join` refused with `already_joined` until someone deleted the file by hand. Now, when this harness session has a stored token for the board, `join` first sends it to `whoami`. On `token_unknown`, `agent_session_revoked` or `agent_session_expired` it joins and replaces the file through the usual write to a temporary file and rename. If the token works, it refuses with `already_joined` as before. On any other failure, such as an unreachable board, it fails with that failure and leaves the file as it was.
- **`join` reads the board once.** With `COOKOUT_URL` unset, the board is the Login's default board, and a `login` running meanwhile can change it. So `join` reads it once and uses that one URL to find the stored token, to ask `whoami` about it and to issue the new one, so a token stored for one board never goes to another. A join by `--code` or by an agent join request goes to that board too, where it used to read only `COOKOUT_URL`.
- **No verb deletes a stored token on a refusal.** Upstream deleted the file on `agent_session_revoked` and `agent_session_expired`, so that `join` could run again. With `join` checking the token itself, that deletion is no longer needed, and it could delete a newer join: a long `cookout watch` that fails after its session joined again would remove the new token. The file now stays until `join` replaces it or a `leave` the board accepts removes it; a `leave` the board refuses keeps it. A verb refused with any of the three codes, with the stored token as its credential, says to run `cookout join --as <name>` again, and the next verb gets the same refusal rather than `not_joined`. Only a successful `leave` deletes the file, and only while it still holds the token that `leave` revoked: `leave` reads the file again after the board accepts the revoke and deletes it only if the token is the same, so a `join` that replaced it meanwhile keeps its new token. A short window between that comparison and the delete remains, and we accept it: a `leave` and a `join` running at once in one harness session ask for opposite outcomes. Every write replaces the file by rename, so concurrent `cookout` processes need no lock.
